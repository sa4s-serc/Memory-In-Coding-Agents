# Classification rationale log

One entry per paper: why the mechanism, scope, role, activity and target were chosen, and what was a judgement call. Result JSONs in `results/` stay as the README specifies; this file is the audit trail. Each paper was decided only from its own PDF and `prompt.md`.

**Decision rules (stricter pass, applies to every entry below).**
- **CROSS** only when the mechanism is intuitively memory carried over from earlier, separate tasks: a store of earlier experience, retained solutions, a skill or function library, or past trajectories reused on later tasks. A curated example or documentation library, a repository or data index, or statistics learned from a training split is not CROSS.
- **CORE** only when the mechanism is itself the paper's headline contribution (the paper is about that memory, context or retrieval mechanism). If the mechanism sits inside a larger agent, framework, tool, system or benchmark, it is COMPONENT. When in doubt, COMPONENT.
- The per-paper entries below were written before this pass. **Where an entry's scope or role disagrees with the table in "Revision" at the end of this file, the Revision table is current** (and `results/` matches it).

## Revision (holistic re-read of every CROSS, after batch 5) - current state

**Test applied.** CROSS needs the paper's own mechanism, as built and evaluated, to carry the outcome of actually executing one task instance (a solution, trajectory, lesson, skill) into a different, later task instance. I stopped counting a paper as CROSS because a store, library or "across tasks" claim appears in it, or because one piece of a larger system keeps something between runs. Within-task evidence, retrieval over fixed or repository-derived material, and persistent plumbing are not CROSS. This replaces my earlier habit of applying the "any part is CROSS" line to side features.

**Demoted from CROSS (6):**
- R00586 ContraFix -> WITHIN. The mechanism is contrastive runtime evidence built for the current vulnerability; accumulated skills are an add-on with a small effect.
- R00526 coding agents as omni-modal solvers -> WITHIN. The finding is that agents write code to extract evidence inside the task; skill injection is a side analysis.
- R00328 harness controller -> WITHIN. The mechanism is a learned policy over context-assembly levers; past trajectories are one of six levers and the static baseline wins.

## Revision (second CROSS tightening, user rule) - current state

**Rule added by the user.** Accumulating something from the past does not make a mechanism CROSS. The store must be something future tasks rely on, and it must be willing to change as tasks progress (updated from task outcomes while the stream runs). A one-shot offline build that is then frozen and only read is not CROSS.

**Applied to the uncertain CROSS papers:**
- R00363 AdaMAST -> EXTERNAL. The taxonomy is induced and validated once and then consumed unchanged; it is a vocabulary, not a store that tasks update.
- R00404 SkillOpt-Lite -> EXTERNAL. One skill document is optimized offline and deployed as a fixed artifact.
- R00521 Skill Issues (lakehouse) -> EXTERNAL. Skill and environment files are optimized offline and then evaluated as fixed artifacts.
- R00606 SkillFlow -> EXTERNAL. The library is built during RL training and frozen at the end.
- Kept CROSS: R00014 (FAISS store gets every new scenario and later ones retrieve it), R00238 (memory written each session and recalled later), R00575 (cache policy edits the map on every invocation), R00371 (library retires and adds skills as the loop runs), R00494 (posteriors updated per verified trajectory), R00475 (store written per problem; finding is that it rarely helps), R00462 (library is curated continually during play and frozen only for the controlled test), R00467 (memory credited and edited as children are evaluated), R00482 (rules are revisable).
